## 2026-10-02：任务保留功能复审

| 优先级 | 问题 | 修复后的行为 |
| --- | --- | --- |
| P1 | 按创建时间清理，老任务刚完成就被删除，等待者拿不到结果 | 按完成时间保留；等待者、批量提交和后台作业取完结果前保护记录，结束后释放 |
| P1 | 把停止轮询的 ERROR／UNCERTAIN 当成可删除记录 | 仅自动清理 SUCCESS、FAILED、CANCEL；待恢复和待核对记录继续保留。删除前在写入队列中重新核对记录，避免扫描期间状态变化后误删 |
| P1 | 设置保存失败，但内存已改为新上限，后续写任务仍会删除旧记录 | RPC 与工具共用存储层入口，先保存再切换；设置和清理按调用顺序执行 |
| P2 | Remote 直连混淆网关外壳与业务结果，隐藏业务失败并换通道重试 | 直连与通用桥共用解包逻辑，先检查网关外层，再检查业务内层；业务失败直接返回 |
| P2 | 官方 Typert manifest 缺少 tasksLimit | 补齐方法，并校验客户端、RPC 和官方 manifest 的清单一致 |
| P2 | 启动时默认上限或已保存的相同上限不会触发清理 | 每次启动应用最终设置并清理一次；待恢复的记录不受影响 |
| P2 | 删除失败仍返回成功，剩余条数也不准确 | 报告实际剩余条数、已删除及失败 ID；自动清理记录警告。设置已保存但清理失败时，面板显示实际设置及错误 |
| P2 | 空配置被转换成 0，意外关闭保留限制；入口接受小数、布尔值等 | 配置、存储和入口共用非负安全整数校验；空配置回退默认 10，显式 0 才表示不限制 |

运行中的轮询更新不再扫描任务目录，并发清理请求会合并。删除了两处重复的设置实现，补充的共用校验模块只处理默认值和整数解析。保留测试使用的临时目录会在结束后清理。

保留上限针对已确认结束的记录，运行、待恢复、待核对和正在取结果的记录另行保留，因此面板总条数可能超过上限。清理任务记录不会删除已经下载的结果文件。

### 保留策略的边界修复（复审发现）

复审逐条核对了上面的 7 项改动：6 项成立，1 项动机正确但落地不完整。另发现 3 个问题，均已修：

| 优先级 | 问题 | 修复后的行为 |
| --- | --- | --- |
| P1 | 待恢复（ERROR）／待核对（UNCERTAIN）被排除出清理**且没有任何上限** —— 「只保留最近 N 条」实际失效，目录无界增长（实测上限 10 时堆到 110 条） | 这两类走**独立上限** `max(20, 2N)`（`0` = 同样不限制）；并且 `saveTask` 对它们也调度清理（原先只在 `canPruneTask` 为真时调度，恰好漏掉这一类） |
| P1 | 模型可见的作业输出（`job.append` / `updateProgress` / `JobOutcome.result`）**不经过任何脱敏** —— 用户提示词里带 Key 时，工具回执会抹、`job_output` 却是明文 | `startTaskJob` 接收脱敏器，`say` / `tick` / 结算结果与失败详情统一过一遍 |
| P2 | 客户端把宿主业务码 `INTERNAL` 当成通道故障 → 换 HTTP **重跑一遍写操作**，并把真正的失败盖成成功（`host/rpc.mjs`、`host/shared.mjs`、工具分发在捕获异常时都返回 `INTERNAL`） | 通道故障只认 **`gateway/` 前缀**（DSH 网关的失败码全部带它）；`client api` / `typert` 从来不是 code（死分支），`internal` 是宿主业务码 —— 拿不准一律按业务失败冒泡，绝不重复执行写操作 |
| P2 | 脱敏 `walk` 对非普通对象原样放行，`Error` 的 `message`/`stack` 因此绕过（当前由上游 `losslessSanitize` 挡着，属潜在旁路） | `Error` 单独处理：降成 `{name,message,stack}` 普通对象后正常脱敏；字节数组 / 日期 / 映射仍原样放行（不拍平） |

另外补了 **7 条**边界测试把上面两条 P1 钉死（此前没有任何测试断言待恢复记录的上限，所以那个洞不会被测试挡住）。
